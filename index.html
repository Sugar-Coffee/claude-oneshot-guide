How we work

Research it. Brief it.
Let Claude build it.

The secret to one-shotting features with Claude Code isn't clever prompting — it's the work you do before you let it run. Research the problem with Claude, write a light brief with links to what you found, and walk away. The brief is the last time you touch it until you're reviewing the output.

01 — The Foundation

Your docs are the cheat code.

Before anything else — before research, before briefs, before one-shotting — you need good project documentation. This is the stuff Claude reads every time it starts a task, and it's the single biggest lever you have over output quality.

Think of it this way: every doc you write is an investment that pays off on every future task. Early on you'll be writing 200-line briefs full of context. Give it a month and your briefs are two sentences and a link to a spec, because the docs do the heavy lifting.

CLAUDE.md — the codebase source of truth

Project structure, naming conventions, file organisation, import patterns, component patterns, how you like things done. Claude reads this at the start of every session. Update it once, every future task gets better — whether you're working interactively or running headless agents.

Architecture specs

How data flows, what the API looks like, which shared packages exist, how state is managed. Claude can poke around the codebase on its own, but a good spec saves it 10 minutes of file-reading and gets it to the right answer straight away.

Code style & test rules

How you structure components, how you name things, what to test, what to skip. All the stuff ESLint can't catch but you'd flag in a PR review. When Claude follows these, the output needs less rework.

Research docs

These are the per-feature docs you build during the research phase (next section). They live in your repo and get referenced in briefs. Over time you build up a library of domain knowledge that makes every related ticket faster.

It compounds

This is the actual cheat code. Not clever prompts, not fancy tooling — clear docs that tell Claude how things work around here. The better your docs, the less context you need in each brief, and the better the output gets. It's a flywheel.

02 — Research

Understand the problem before you solve it.

This is where most of the human value lives. Before you write a single line of a brief, work with Claude to understand the problem space. Explore the existing platform, look at how the feature works in legacy systems, dig into the API, study how other products in the industry have solved it.

The research phase is interactive and collaborative. You're talking to Claude, asking it to read files, explore APIs, pull apart existing implementations. The goal is to produce research documents — structured write-ups that capture everything the agent will need to know when it's time to build.

Explore the existing platform

Get Claude to read through your codebase's existing implementation of related features. How do similar components work? What patterns do they follow? What state management approaches are in play? Claude builds a picture of how things work around here — and documents it so the building agent doesn't have to rediscover it all.

Understand the API and data model

Have Claude dig into the API — queries, mutations, types, data shapes. If there's a legacy system involved, get it to document the quirks, the edge cases, the things that aren't obvious from the schema alone. This is the domain knowledge that makes or breaks a one-shot.

Study industry implementations

This is the stuff Claude wouldn't find during its own planning phase — research that lives outside your codebase. How do other products solve this problem? What are the established UX patterns? What are the trade-offs between different approaches? Building a flashcard feature? Look at how Anki, Quizlet, and Duolingo handle it. Building a payment flow? Study Stripe's checkout patterns. Building a rich text editor? Look at how Notion and Linear approach it. Claude can help you research all of this and document the decisions you make.

Explore third-party docs and integrations

If your feature touches external services, SDKs, or libraries, this is the time to research them. Get Claude to read through the docs, understand the API surface, and document the integration approach. The building agent won't always dig deep into external docs during its run — so anything it should be completely aware of in third-party services should be captured in your research docs.

Produce research docs

The output of all this is one or more research documents that live in your repo. API shapes, data models, component patterns, design decisions, edge cases, industry trade-offs, third-party integration details. These docs become the knowledge base that future briefs reference — write them once, use them forever.

This is where you add the most value

Research is the phase where human judgement matters most. You're deciding what to flesh out, how it works in other industries or apps, what trade-offs to make. The agent can help you explore and document it all. Once the research is done and the docs are written, everything after this point is mostly autopilot.

The key insight is that Claude's planning phase — which runs automatically before it starts building — can explore your codebase, but it can't explore the wider world. Industry best practices, third-party documentation, design patterns from other products, business context that lives in someone's head — all of that needs to be captured in research docs so the agent has it when it needs it.

Think about two types of research docs. The first type is feature-specific — a deep dive into the API surface, data model, and design decisions for a particular feature. These get linked directly in the brief and feed straight into the planning phase. The agent reads them, understands the domain, and plans accordingly. The second type is repo-wide — broader documentation about how your platform works, how services connect, what patterns are established. These live permanently in your repo and serve every future task. An architecture overview, a guide to your state management approach, a map of your API layer — these are the docs that mean you never have to explain the same thing twice.

Get Claude to generate both types during research. Ask it to explore the codebase and produce a write-up of how a related system works. Ask it to document the API surface for a feature area. Ask it to summarise the patterns it found across similar components. These generated docs become part of your project's knowledge base — they feed into the planning phase for the current feature, and they're there for every future feature that touches the same area. The more research docs you accumulate, the less research each new feature needs.

03 — The Brief

Your brain dump + links. That's it.

The brief is the last time you really touch this before reviewing the output. It's a brain dump — everything you know about what needs building, poured into a document along with links to everything you've gathered. Your research docs, Figma designs, reference repositories, third-party API docs, example implementations from other projects. Anything that gives Claude the full picture.

Keep it goal-oriented. Describe the outcome, not the steps. You're not writing implementation details or telling Claude which files to create. You're describing what the feature does, what it should look like, what constraints it has, and then pointing at everything it needs to figure out the rest. That's the whole point of investing in the research phase — so the brief can be a light pointer to heavy docs.

A good brief has a short description of the feature, links to every research doc you produced, links to the Figma designs (specific frames, not just the whole file), any reference implementations worth looking at (other components in your codebase, open-source repos that solve a similar problem), acceptance criteria so Claude knows what "done" looks like, and any constraints that aren't captured elsewhere.

What you don't need: file paths, function signatures, step-by-step implementation instructions. The research docs cover the domain knowledge. The CLAUDE.md covers the project conventions. The Figma designs cover the UI. The brief just ties it all together. If your research was thorough, the brief almost writes itself — it's mostly links and a sentence or two about what you want.

What to include vs what to skip

If the agent can find it in the codebase, skip it. If it's in your research docs, link to them. Only put things in the brief that aren't captured anywhere else — Figma links, acceptance criteria, reference repos, constraints specific to this feature. The lighter the brief, the better (as long as everything is linked or documented somewhere). Over time, as your project docs get richer, your briefs get shorter.

04 — Planning

Claude plans it for itself. Don't read it.

Once you hand over the brief, the first thing that happens is a planning phase. This runs on autopilot and it's one of the most powerful parts of the whole workflow — and you're not involved at all.

We use planning skills that generate structured documents the agent uses as its own internal brief. The flow looks like this:

Brief → Brainstorm → Design Doc → Impl Plan → Execution
Brainstorm → Design document

A brainstorming skill kicks off first. The agent digs through the codebase, reads your research docs and specs, and produces a design document — everything it learned, its decisions on approach, and a structured brief for the work. It's like a scoped ticket the agent writes for itself, auto-generated from your brief and the project context.

Writing plan → Implementation plan

From that design doc, a writing plan skill generates a detailed implementation plan. These things are often 1,000+ lines — every file to touch, every component to create, every edge case, the order of operations. Way more thorough than anything you'd write yourself.

Nobody reads any of this

This is the key bit. These documents are food for the agent, not for you. They exist so the agent has a solid brief it wrote for itself before it starts coding. If something's off in the plan, you'll spot it in the output — that's what the review phase is for.

The planning phase takes a few minutes. During that time the agent is doing the work of a senior dev scoping a ticket — reading the codebase, understanding patterns, deciding on an approach, writing it all up. It does this every single time and never cuts corners. Your research docs are what make this phase really sing — the agent isn't guessing at the domain, it's reading your documented decisions.

Why not just skip to building?

You could skip planning and let Claude start coding immediately. But the planning phase is what turns a good brief into a great implementation. It's the difference between a PR that needs one round of fixes and one that needs three. The few minutes it takes pays for itself every time.

05 — The Build

Walk away. Don't interrupt.

This is the discipline part. Once Claude starts building, leave it alone. Don't watch the diffs scroll by. Don't jump in to correct something mid-flow. Don't say "actually, do it this way instead." Go make a coffee. Work on something else. Come back when it's done.

Interrupting an agent mid-build is almost always worse than letting it finish and fixing things afterward. When you interrupt, you break its context, force it to re-orient, and often end up with a messier result than if you'd just let it run. The agent has a plan — let it execute.

Why non-interference works

Claude's planning phase built a detailed implementation plan. It knows what files to touch, in what order, how they connect. When you interrupt mid-way, you're inserting yourself into the middle of that plan. The agent has to reconcile your change with everything it was about to do. It's like grabbing the steering wheel from someone who's already navigating — you might think you're helping, but you're usually just making it swerve.

The one exception: if you spot something fundamentally wrong — like it's building against the wrong API or implementing a completely different feature — then yes, stop it. But "I'd have named that variable differently" or "I'd have used a different component" — save those for the review. That's what the review phase is for.

06 — Review & Remediation

Check the output, not the process.

The build is done. Now you review. The key mindset shift here is that you're reviewing the output — does it work, does it look right, does it match the brief — not the process. You don't need to read every line of the diff. You need to check that the feature works.

Automated checks first

Run the build. Run the tests. Run a code review skill if you have one. Let the tools tell you where to look before you start reading code yourself. If the build passes and tests pass, you're already in good shape.

Check the UI against the designs

Pull up the Figma designs. Click through the feature. Does it match? This is where you'll catch most of the issues — spacing, colours, animation timing, responsive behaviour. The functional stuff is usually solid; the visual polish is where humans still add the most value.

Remediate with bullet lists

Don't rewrite the brief. Don't start over. Write a specific, actionable list of fixes: "the card flip animation should be 300ms not 200ms," "the progress bar is missing on mobile," "the end scene needs a retry button." Specific, testable, one per line.

One or two rounds of fixes and you're shipping. After a few features you get a feel for what to check and the remediation lists basically write themselves.

Bullet lists, not re-prompts

Remediation is not re-prompting. You're not explaining the feature again. You're giving Claude a checklist of specific fixes in the same session, with all its context intact. It reads your list, fixes each item, and you review again. This is far more efficient than starting fresh or rewriting the brief.

How to write good remediation lists. Each item should be specific and testable — something Claude can act on without asking clarifying questions. "Fix the spacing" is vague. "The gap between the card and the progress bar should be 16px, not 24px" is actionable. Reference the specific component or screen. If there's a design to match, say which Figma frame. If there's a behaviour issue, describe what it does vs what it should do.

Keep each item independent. Don't chain them with "and then" or "after that" — just list them. Claude works through the list one by one and the order rarely matters. If something does depend on something else, say so explicitly: "Once the card flip is fixed, the progress bar animation should trigger on flip completion."

Don't re-explain context Claude already has. It's the same session — it built the feature, it knows the codebase, it has your brief and research docs loaded. Just tell it what's wrong and what "right" looks like. Think of it like leaving comments on a PR, not writing a new ticket.

07 — Automate It

Once you're working this way, automate the whole thing.

Here's the payoff. Once you're naturally working in this flow — research, brief, plan, build, review, fix — you can automate it. The brief becomes a ticket. The planning phase runs headlessly. The build happens while you sleep. You wake up to a PR.

Stokowski is an open-source orchestrator that does exactly this. It polls your ticket system (Linear) for issues in "Todo," spins up isolated Claude Code agents, and runs each ticket through a configurable state machine — with human gates wherever you want them.

Ticket in Todo → Agent investigates → Gate (optional) → Agent builds → PR for review → Merge

The whole pipeline is defined in YAML. Each stage is either an agent stage (Claude does the work) or a gate (you review and approve or request rework). Start with gates on everything while you build trust, then progressively remove them as you see the output quality is consistent.

A pipeline with human checkpoints workflow.yaml 
states:
  investigate:        # agent researches the ticket
    type: agent
  research-review:    # you check the investigation
    type: gate
    rework_to: investigate
  implement:          # agent builds the feature
    type: agent
  code-review:        # you review the PR
    type: gate
    rework_to: implement
  merge:              # agent merges on approval
    type: agent

When a gate rejects work, the agent gets your feedback and re-enters the rework_to stage — same session, all context preserved. It's the automated version of your bullet-list remediation.

Once you trust the pipeline, trim the gates. Bug fixes, test additions, small features with clear specs — these can run fully gateless. Ticket in, PR out, you just review and merge.

A gateless pipeline workflow.yaml 
states:
  implement:
    type: agent
    prompt: prompts/implement.md
    transitions:
      complete: done
  done:
    type: terminal

It gets really interesting when you connect this to monitoring. Sentry catches an error — creates a ticket. Stokowski picks it up, the agent investigates and fixes, PR appears. You just review and merge. Multiple agents can run concurrently too — one building a feature, one fixing a bug, one adding tests.

Everything you've learned still applies

The research docs you wrote? Stokowski's agents read them. Your CLAUDE.md? Every headless agent loads it. The brief format? That's your ticket now. The remediation flow? That's the rework loop. Nothing changes except who triggers each step — you or the orchestrator. The habits you build working interactively are exactly what make automation work.

Claude Code Tips

Stuff that makes life easier.

Shortcuts, features, and configuration tricks we use all the time.

⚡ opusplan

Use claude --model opusplan to get the best of both models. Opus handles the planning and architectural reasoning, then Sonnet takes over for the actual code generation. You get Opus-quality decisions at Sonnet speed — and it costs roughly 40% less than running full Opus.

⚡ .claudeignore

Use a .claudeignore file (same syntax as .gitignore) to exclude files and directories Claude doesn't need — build output, vendor folders, generated code. On a typical Node project this can cut 25% of the tokens Claude spends reading your repo, leaving more room for the actual feature work.

⚡ Ctrl+G — editor mode

Use Ctrl+G to open your system text editor (respects $EDITOR) for composing prompts. For the kind of multi-paragraph briefs that enable one-shotting, a proper editor is far better than the single-line terminal input. Write your brief in VS Code or Vim, save and close, and it sends.

⚡ Hooks

Configure PostToolUse hooks in your .claude/settings.json to auto-run Prettier or your formatter every time Claude edits a file. Code is always formatted to your standards — one less thing to catch in review. PreToolUse hooks can block certain actions before they happen.

⚡ /btw

Use /btw to give Claude context without disrupting its current task. "btw, the API endpoint changed to /v2/flashcards" — Claude absorbs the info and keeps going. It's the difference between a tap on the shoulder and pulling someone out of deep focus.

⚡ Subagents + Ctrl+B

Claude can spawn focused subagents for parallel work — each with its own context window. If a feature touches multiple packages, separate agents handle each one concurrently and merge the results. Ctrl+B pushes a subagent to the background while you continue in the main session.

⚡ Esc Esc — undo

If something went wrong, Esc Esc (double-tap Escape) restores your code and conversation to a previous point — cleaner than Ctrl+C because it actually reverts the changes rather than just stopping.

⚡ Option+T — extended thinking

Use Option+T (Alt+T on Linux/Windows) to toggle extended thinking mid-session. When Claude is struggling with a subtle bug, switching on extended thinking gives it deeper reasoning without restarting the conversation. Toggle it off again for straightforward fixes.

⚡ Permission modes

For fully autonomous runs, use --dangerously-skip-permissions to bypass all permission prompts, or --allowedTools to restrict which tools are available — keeping things safe even without a human in the loop.
